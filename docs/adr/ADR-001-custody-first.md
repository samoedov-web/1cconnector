# ADR-001. Режим `custody_mode = active`: custody-first учёт

Статус: **дизайн-заметка, кода нет** (по specs/depository-adapter.md,
п. 4.7 — режим включается заглушкой с явной ошибкой до вступления
требований в силу и появления API депозитариев).

## Контекст

С 01.07.2027 учёт и хранение цифровой валюты переходят к цифровым
депозитариям из реестра ЦБ. Юридически главной первичкой становится
**выписка депозитария**; блокчейн-запись — доказательная база второго
уровня. Сегодня продукт работает chain-first: финальная транзакция →
матчинг → курс → ФИФО → документ 1С. Режим `shadow` уже даёт сверку
двух источников без влияния на учёт.

## Решение (дизайн будущего режима)

### 1. Источник истины

- В `active` первичкой для **генерации документов 1С** становится
  `CustodyEntry` (строка выписки); `LedgerEntry` (блокчейн) остаётся
  обязательной доказательной базой второго уровня.
- Конвейер (`pipeline.py`) получает абстракцию «учётного события»
  (AccountingEvent) с двумя реализациями: from-chain (текущая) и
  from-custody. Выбор — по `custody_mode`; сами движки (матчинг, курсы,
  ФИФО) не меняются — меняется вход.
- Строка выписки, не подтверждённая цепочкой (missing_on_chain),
  порождает документ **только после ручного разбора** — защита от ошибок
  депозитария. Настройка `custody_strict` (on): без подтверждения
  цепочкой документ не создаётся вовсе.

### 2. Генерация документов 1С

- Идемпотентность обмена переезжает с ключа `сеть:хэш:log_index:тип` на
  `custody:источник:statement_id:entry_id:тип`. Оба ключа сосуществуют:
  старые документы не пересоздаются (см. миграцию ниже).
- «Поступление/Выбытие ЦВ» несут ссылку на строку выписки + (если есть)
  хэш транзакции; рублёвая оценка — по курсу на дату строки выписки
  (момент признания по выписке, а не по финальности) — **вопрос к
  методологу**, зафиксирован в specs/questions.md при реализации.
- Комиссии: если депозитарий выделяет fee-строки — из них; иначе прежний
  механизм (receipt/gettransactioninfobyid) остаётся для доказательной
  оценки.
- ФИФО-партии строятся от custody-событий; регистр партий 1С не меняется.

### 3. Миграция клиента shadow → active

Пошагово, без повторного внедрения (цель спеки):

1. Клиент работает в `shadow` ≥ одного полного отчётного периода;
   критерий готовности — N подряд сверок без расхождений класса
   `missing_*` (допускаются разобранные вручную).
2. Выбирается **дата среза** (граница отчётного периода). Все документы
   до среза — chain-first (остаются как есть), после — custody-first.
3. Включение `active` требует: действующей сверки за последний период
   без неразобранных расхождений + подтверждения администратора (двойное
   подтверждение в панели). Иначе — отказ с диагностикой.
4. Партии ФИФО на дату среза фиксируются актом остатков (печатная форма);
   custody-события продолжают те же партии — непрерывность себестоимости.
5. Откат: `active → shadow` разрешён всегда (учёт возвращается к
   chain-first с даты отката); документы, созданные из custody-событий,
   не удаляются (неизменяемость), помечаются источником.

### 4. Обратная совместимость

- `off` и `shadow` работают без изменений навсегда (клиенты вне
  требований — иностранные юрисдикции, тестовые контуры).
- Интерфейс `DepositoryAdapter` версионируется (`adapter_api_version`);
  реальные адаптеры объявляют совместимость, загрузчик отклоняет
  несовместимые с текущим ядром версии.
- Документы 1С получают реквизит «ИсточникПервички» (chain | custody) —
  расширение уже спроектировано с КлючомОбмена, добавление реквизита
  не ломает существующие документы.
- Отчётные формы (акт по платежу, журнал, налоговый регистр) дополняются
  реквизитами выписки; журнал неизменяемости показывает обе первички.

## Последствия

- Кодовая база уже готова структурно: DataSource/CustodySource, выписки
  в журнале неизменяемости, движок сверки, регистр в 1С — остаётся
  переключатель входа конвейера и миграционная механика.
- Оценка реализации active после выхода подзаконных актов: 2–4 недели
  (адаптер конкретного депозитария — отдельно, тонкий, по контракту
  DepositoryAdapter).

## Открытые вопросы (дополнять при выходе актов)

1. Момент признания дохода/расхода: дата строки выписки или дата
   финальности в цепочке? (влияет на курс пересчёта).
2. Формат учётного номера операции у депозитариев — войдёт ли в справки
   валютного контроля вместо/вместе с хэшем.
3. Требования к хранению выписок (срок, формат, ЭП депозитария) —
   возможно расширение CustodyStatement полями подписи.
