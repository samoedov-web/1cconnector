# Продукт 2. Коннектор «Блокчейн → 1С» — архитектура и ТЗ для разработчиков

> Назначение документа: техническое задание уровня архитектуры для команды разработки. Продукт: сервер, который автоматически собирает транзакции по кошелькам компании из блокчейнов, обогащает их учётными данными и выгружает в 1С готовые документы и проводки для учёта расчётов по ВЭД в цифровой валюте.

---

## 1. Принципы (не обсуждаются)

1. **Read-only по отношению к блокчейну.** Система никогда не хранит приватные ключи и не подписывает транзакции. Только чтение публичных данных сетей. Это радикально снижает поверхность атаки, требования к безопасности и страхи клиента.
2. **1С — мастер-система учёта.** Коннектор не заменяет учёт, а поставляет в 1С первичные данные и проекты документов. Проведение — на стороне бухгалтера (авто-проведение — опционально, по настройке).
3. **Неизменяемость первички.** Каждая импортированная транзакция хранится с хэшем, сырым ответом ноды и меткой времени получения — доказательная база для проверок.
4. **On-premise по умолчанию.** Данные о кошельках и оборотах компании чувствительны; клиенты (особенно после аудита схем) не захотят отдавать их в чужое облако. Облачная версия — вторым этапом.
5. **Обновляемость форм отчётности.** Формы для ФНС/банков будут меняться подзаконными актами — печатные формы и выгрузки выносятся в обновляемые шаблоны, а не зашиваются в код.

---

## 2. Архитектура высокого уровня

```
+----------------------+     +------------------------+     +---------------------+
|  Blockchain Indexer  | --> |  Core Service + DB     | --> |  1C Integration     |
|  (TRON, EVM chains)  |     |  (matching, pricing,   |     |  (расширение 1С +   |
|  ноды / провайдеры   |     |   accounting engine)   |     |   HTTP API обмена)  |
+----------------------+     +------------------------+     +---------------------+
        |                              |                              |
   RPC/REST к нодам          PostgreSQL, журнал           1С:БП 3.0 / КА / ERP
   webhooks провайдеров      неизменяемости, RBAC         через план обмена
```

Три контура: **индексер** (сбор), **ядро** (обработка), **интеграция с 1С** (доставка). Плюс веб-панель администратора (настройка кошельков, разбор нераспознанных транзакций, мониторинг).

---

## 3. Модуль индексации

**Задача:** по списку отслеживаемых адресов собирать все входящие/исходящие транзакции с гарантией полноты.

- Сети MVP: **TRON (TRC-20 USDT)** и **Ethereum (ERC-20 USDT/USDC)** — это покрывает подавляющую часть ВЭД-расчётов. Архитектура — плагинная: интерфейс `ChainAdapter`, чтобы добавить BNB Chain/Polygon/TON без переписывания ядра.
- Источники данных: собственная лёгкая нода ИЛИ внешние RPC-провайдеры — конфигурируемо, минимум два источника на сеть с кросс-проверкой (защита от отдачи неполных данных одним провайдером).
- **Обработка реоргов:** транзакция получает статусы `seen → confirmed(N) → final`. Порог финальности N — настройка per-network (та же таблица, что в договорной оговорке Продукта 1 — это принципиально: учётная финальность = договорная финальность).
- Догрузка истории: при добавлении адреса — полный бэкфилл с указанной даты.
- Дедупликация по (сеть, хэш, log index).

## 4. Модуль курсов

- Источники котировок — те же, что зафиксированы в учётной политике/договоре клиента (настройка: основной + резервный источник).
- Снимок курса сохраняется на момент финальности каждой транзакции и на даты переоценки; история курсов неизменяема.
- Пересчёт: актив → валюта контракта → рубль, с сохранением всех промежуточных значений и источника.

## 5. Модуль сопоставления (matching) — ключевая ценность продукта

**Задача:** привязать каждую транзакцию к контрагенту, контракту ВЭД и инвойсу.

- Правила автоматчинга (в порядке приоритета):
  1. адрес отправителя/получателя ∈ справочника адресов контрагента → контрагент;
  2. сумма ± допуск и валюта совпадают с открытым инвойсом контрагента → инвойс;
  3. период платежа в окне ожидания по графику контракта.
- Всё, что не сматчилось автоматически, попадает в **очередь ручного разбора** в веб-панели (оператор привязывает вручную, система запоминает правило).
- Частичные оплаты и переплаты: разнесение одной транзакции на несколько инвойсов и наоборот.
- Результат матчинга — основа для справок валютного контроля: «платёж X по контракту Y (учётный номер Z)».

## 6. Модуль учёта (accounting engine)

- Генерация проектов документов 1С по событиям:
  - поступление цифровой валюты (входящий платёж по контракту);
  - выбытие цифровой валюты (оплата поставщику / продажа за рубли);
  - переоценка на отчётную дату (бухгалтерская: разницы оценки остатков;
    в налоговую базу НЕ включается — по ст. 282.3 НК цифровая валюта для
    налога на прибыль не переоценивается и «курсовых разниц» не образует;
    ред. уточнение 2026-07-15 по итогам внешнего ревью);
  - комиссия сети как отдельная статья расходов.
- Метод оценки выбытия: **ФИФО** (по партиям поступления, с хранением себестоимости каждой партии) — заложить возможность смены метода настройкой.
- Мэппинг на план счетов — конфигурируемый (счета учёта цифровой валюты, разниц оценки при переоценке, комиссий задаются при внедрении под учётную политику клиента; преднастроенный дефолтный вариант поставляется, финальный мэппинг утверждает главбух/аудитор клиента).
- Налоговый слой: регистры для расчёта налоговой базы по операциям с цифровой валютой (доход/расход, рублёвая оценка по правилам НК с учётом поправок 2024–2026), выгрузка в декларационные регистры 1С.

## 7. Модуль отчётности

- Печатные формы (обновляемые шаблоны):
  - справка/акт по крипто-платежу для банка и цифрового депозитария (агенты валютного контроля);
  - журнал операций по адресу за период (для отчёта в ФНС по операциям через иностранные кошельки);
  - акт сверки с контрагентом (RU/EN) — совместим с шаблоном из Продукта 1.
- Экспорт: PDF, XLSX, а также машиночитаемый формат под будущие электронные форматы ФНС (структуру держать готовой к маппингу, форматы выйдут подзаконными актами).
- **Журнал неизменяемости:** для каждой строки отчёта — ссылка на исходную транзакцию, хэш, сырой ответ ноды.

## 8. Интеграция с 1С

- Поставка: **расширение конфигурации** (без изменения типовой) для 1С:Бухгалтерия 3.0, далее КА/ERP.
- Объекты расширения:
  - справочники: «Криптоактивы», «Блокчейн-сети», «Кошельки/Адреса» (свои и контрагентов), «Источники котировок»;
  - документы: «Поступление цифровой валюты», «Выбытие цифровой валюты», «Переоценка цифровой валюты»;
  - регистры: партии ЦВ (для ФИФО), курсы, привязки к договорам ВЭД (связь со стандартным справочником «Договоры»).
- Транспорт: HTTP-сервис на стороне 1С (REST) + фоновое задание синхронизации; аутентификация по токену; идемпотентность обмена (повторная выгрузка не создаёт дублей — ключ по хэшу транзакции).
- Режимы: «проекты документов» (бухгалтер проводит вручную) / «авто-проведение» (по настройке).
- Стратегически: пройти сертификацию **«1С:Совместимо»** — открывает канал продаж через франчайзи 1С.

## 9. Безопасность и доступы

- Никаких приватных ключей нигде и никогда (принцип 1).
- RBAC: администратор / оператор разбора / только чтение (аудитор).
- Аудит-лог всех действий пользователей (кто привязал транзакцию, кто изменил правило).
- Шифрование БД в покое, TLS в транзите; секреты — в защищённом хранилище.
- Пентест перед первым коммерческим релизом (это же аргумент продаж).

## 10. Нефункциональные требования

- Развёртывание: Docker Compose (on-prem, один сервер клиента); системные требования умеренные — объёмы данных у одного клиента невелики (тысячи транзакций/год).
- Лицензирование: годовая лицензия с онлайн- или файловой активацией; тиры по числу отслеживаемых адресов и сетей; grace-режим при просрочке (чтение доступно, синхронизация останавливается).
- Автообновления шаблонов отчётности отдельно от обновлений ядра (связь с Продуктом 3 — подписка доставляет новые формы).
- Мониторинг: health-check индексеров, алерты при отставании от сети, при расхождении источников данных.

## 11. Рекомендации по стеку

- Backend: Python (FastAPI) или Go — по компетенциям нанятой команды; PostgreSQL; Redis для очередей; Celery/worker для индексации.
- Веб-панель: любой зрелый SPA-фреймворк, панель простая.
- 1С-часть: разработчик 1С с опытом расширений и HTTP-сервисов (отдельная роль, не совмещать с backend).
- Блокчейн-часть: не писать парсеры с нуля там, где есть проверенные библиотеки для TRON/EVM.

## 12. Дорожная карта

**MVP (цель — до/к 01.07.2026, старт продаж в переходное окно):**
- TRON + Ethereum, USDT/USDC; индексация, финальность, курсы;
- матчинг с ручным разбором; поступление/выбытие/ФИФО;
- выгрузка в 1С:БП 3.0 (проекты документов);
- печатные формы: акт по платежу, журнал операций.

**v1 (через 3–4 месяца после MVP):**
- переоценка (бухгалтерская) и налоговые регистры (только реализованные операции);
- авто-проведение; сертификация «1С:Совместимо»;
- отчёты под вышедшие подзаконные формы ФНС.

**v2:**
- КА/ERP; дополнительные сети; облачная multi-tenant версия;
- API для депозитариев/обменников (когда реестр ЦБ заработает — прямые выписки вместо парсинга сетей);
- модуль сверки с выпиской депозитария.

## 13. Команда и организация разработки (с учётом ваших рисков)

- Состав: 1 backend (ядро+индексер), 1 разработчик 1С, 1 фронтенд на неполной загрузке, вы — продакт/архитектор. QA — аутсорс на релизы.
- **Оформление: подряд или найм на ваше юрлицо. IP на весь код — у юрлица по договору (служебное произведение / отчуждение прав). Не доля, не 50/50, не «потом договоримся».**
- Репозиторий, CI, доступы — на юрлицо с первого дня.
- Реалистичный срок MVP такой командой: 4–6 месяцев активной разработки. Значит, если целиться в переходное окно 2026–2027 — старт разработки не откладывать, а первые 1–2 внедрения делать в полуручном режиме параллельно с разработкой (они же дадут реальные ТЗ на формы и проводки).
