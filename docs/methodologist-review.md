# Контрольная точка с методологом: сверка блокчейн ↔ депозитарий

Пакет для проверки движка сверки (specs/depository-adapter.md, контрольная
точка после фазы 4). Здесь: как устроена сверка на языке учёта, 12 готовых
контрольных примеров, как добавить свои, и вопросы, требующие вашего решения.

## Как проверить (два способа)

**Быстрый (без установки чего-либо, кроме Python):**

```bash
python scripts/reconciliation_demo.py
```

Скрипт прогоняет 12 контрольных примеров из этого документа через реальный
движок и сверяет с ожиданиями; расхождение — ненулевой код выхода. Ваши
примеры добавляются в список CASES по образцу (двусторонняя таблица
платежей → ожидаемые статусы) — попросите разработчика или добавьте сами.

**Полный (через панель):** развернуть коннектор (docs/pilot-quickstart.md),
включить `CONNECTOR_CUSTODY_MODE=shadow`, сгенерировать выписку из реальных
данных с искажениями (docs/custody-fixtures.md) и пройти поток во вкладке
«Сверка».

## Что сверяется и как

Со стороны цепочки берутся только **финальные** транзакции периода; со
стороны депозитария — строки загруженных выписок (хранятся неизменяемо,
как получены). Правила применяются по убыванию надёжности:

1. **По хэшу транзакции** — если депозитарий его отдаёт. Совпал хэш, но
   не сумма — фиксируем «расхождение суммы» с дельтой (типовой случай:
   комиссия удержана внутри суммы).
2. **По совокупности признаков**: актив (с учётом таблицы соответствий
   тикеров), сумма ± допуск, дата ± окно, направление.
3. **Агрегаты**: одна строка выписки = несколько платежей за день (и
   наоборот). Частичное покрытие — расхождение с дельтой.
4. Остальное — расхождения двух видов («нет в выписке» / «нет в цепочке»),
   уходят оператору в очередь ручного разбора.

Настройки на клиента: допуск абсолютный и относительный, окно дат,
авто-принятие агрегатов (можно требовать ручное подтверждение каждого).

## Контрольные примеры (исполняются скриптом)

| № | Ситуация | Ожидание движка |
|---|---|---|
| К1 | Идеальный месяц, у депозитария есть хэши | все «совпало» |
| К2 | Депозитарий потерял платёж | «нет в выписке» |
| К3 | В выписке лишняя операция | «нет в цепочке» |
| К4а | Комиссия 15 USDT внутри суммы, допуск 0 | «расхождение суммы», дельта −15 |
| К4б | Та же комиссия, допуск 20 (учётная политика) | «совпало» |
| К5а | Выписка датирует платёж следующим днём, окно 48 ч | «совпало» |
| К5б | То же, окно 6 ч | «расхождение даты» |
| К6 | Строка выписки = 5 платежей за день | «совпало (агрегат)» |
| К7 | Агрегат покрыл 4 из 5 | «расхождение суммы», дельта −100 |
| К8 | Строка выписки задвоена | 1 «совпало» + 1 «подозрение на дубль» |
| К9 | Авто-принятие агрегатов выключено | «ручной разбор» |
| К10 | Относительный допуск 0.1% на платеже 1 млн | «совпало» при −0.05% |

## Вопросы, требующие вашего решения (из specs/questions.md)

1. **Тикер против хэша.** Если хэш транзакции совпал, но тикер актива в
   выписке другой — сейчас движок считает это совпадением (хэш однозначен,
   тикеры депозитариев различаются). Альтернатива: помечать «на ручной
   разбор». Что корректнее для доказательной базы?
2. **Значения по умолчанию.** Какие допуск и окно дат предложить как
   дефолт в поставке (сейчас: допуск 0, окно 24 часа, агрегаты — авто)?
3. **Комиссия внутри суммы.** К4б принимает такие строки при достаточном
   допуске. Нужно ли отдельно вычленять комиссию как расход (сейчас она
   растворяется в допуске) — влияет на будущий режим active.
4. **Момент признания** (задел на active, ADR-001): дата строки выписки
   или дата финальности в цепочке — что станет датой операции для курса?
