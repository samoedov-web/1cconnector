# Депозитарная сверка: движок, режимы, поток оператора

Реализация specs/depository-adapter.md (фазы 1–6). Слой готовит продукт к
эпохе цифровых депозитариев: когда появятся их API, интеграция — тонкий
адаптер по контракту `DepositoryAdapter`, включение у клиента — настройкой.

## Режимы (`CONNECTOR_CUSTODY_MODE`)

| Режим | Поведение |
|---|---|
| `off` (по умолчанию) | Текущее поведение продукта, custody-слой не активен; эндпоинты сверки отвечают 403 с инструкцией |
| `shadow` | Загрузка выписок, сверка, акты, вкладка «Сверка»; в 1С — только информационный регистр; **источник истины для учёта — блокчейн, ноль влияния на проводки** |
| `active` | Заглушка: 501 с явным сообщением; дизайн перехода — docs/adr/ADR-001-custody-first.md |

Неизвестное значение — ошибка старта (валидация настроек).

## Архитектура

```
DataSource
├── ChainAdapter (chain)         TRON, Ethereum — индексер
└── DepositoryAdapter (custody)  meta / capabilities / fetch_statements /
                                 fetch_entries / health
```

- Выписки (`CustodyStatement` + `CustodyEntry`) хранятся в журнале
  неизменяемости: сырой payload + SHA-256, на PostgreSQL — триггеры
  запрета изменений; конфликт содержимого при том же statement_id —
  ошибка, не перезапись.
- `capabilities()` объявляет возможности депозитария (хэши, контрагенты,
  сеть, гранулярность per_tx/aggregated/mixed) — движок работает при
  любой комбинации.
- До появления реальных API — `MockDepositoryAdapter` на фикстурах
  (docs/custody-fixtures.md) с генератором искажений.

## Движок сверки

Вход: финальные транзакции периода ↔ строки выписок источника.
Каскад по убыванию приоритета:

1. дубликаты строк выписки → `duplicate_suspect` (не двойной матч);
2. по `external_tx_hash` — точное соответствие (сумма вне допуска при
   совпавшем хэше → `amount_mismatch` с дельтой);
3. по кортежу (актив после маппинга, сумма ± допуск, дата ± окно,
   направление); очевидные пары с расхождением → `amount_mismatch` /
   `date_mismatch`;
4. агрегаты в обе стороны (1 ↔ N); частичное покрытие → `amount_mismatch`
   с дельтой; при выключенном авто-принятии — `manual`;
5. остатки → `missing_in_custody` / `missing_on_chain` → очередь ручного
   разбора во вкладке «Сверка».

Конфигурация per-client: `tolerance_abs`, `tolerance_rel`, `date_window`,
`accept_aggregates`. Тикеры выписки приводятся через
`custody_asset_mapping` (source_id, тикер → актив системы).

Свойства: детерминированность (одинаковый вход → одинаковый результат),
идемпотентность (повторный запуск с той же конфигурацией возвращает
существующий результат), полный аудит (каждая строка результата несёт
правило и объяснение). После реорга затронутые запуски автоматически
помечаются **stale** — повторный запуск обязателен и даёт консистентный
итог.

## Поток оператора (вкладка «Сверка», режим shadow)

1. «Загрузить выписки» за период — адаптер → журнал неизменяемости
   (повторная загрузка идемпотентна).
2. «Запустить сверку» с настройками допусков/окна.
3. Смотреть сводку и детализацию; расхождения — «Разобрать» с
   комментарием (статус `manual`, прежний статус и автор — в аудите).
4. Печать: «Акт сверки: блокчейн ↔ депозитарий» (HTML/XLSX/JSON) —
   шаблон обновляемый (templates/reports/custody_reconciliation.html).
5. В 1С фоновым заданием уходит информационная запись в регистр сведений
   «РезультатыСверкиСДепозитарием» (сводка + расхождения). Никаких
   бухгалтерских документов.

## Подключение реального депозитария (будущее)

1. Реализовать класс по контракту `DepositoryAdapter`
   (`src/connector/custody/base.py`), зарегистрировать:
   `@register_custody_source("depo-x")`.
2. Объявить honest `capabilities()` — движок подстроится.
3. Указать `CONNECTOR_CUSTODY_SOURCE_ID=depo-x` и конфигурацию адаптера.
4. Прогнать в `shadow` минимум отчётный период, свести маппинг активов.
5. Переход в `active` — по ADR-001 (после вступления требований в силу).
