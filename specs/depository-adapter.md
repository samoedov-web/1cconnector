# ТЗ для Claude Code: DepositoryAdapter — слой депозитарной сверки (режим «одной галочки»)

> **Как использовать:** положить этот файл в корень репозитория (например, `specs/depository-adapter.md`), сослаться на него в `CLAUDE.md` и выдавать Claude Code задачи по фазам (раздел 9). Не выдавать всё ТЗ одной задачей — по фазе за сессию, с ревью и тестами между фазами.

---

## 1. Контекст (что уже есть)

Продукт — коннектор «Блокчейн → 1С» для учёта расчётов по ВЭД в цифровой валюте:

- **Индексер** (TRON, Ethereum; USDT/USDC) с плагинным интерфейсом `ChainAdapter`, статусы транзакций `seen → confirmed(N) → final`, обработка реоргов;
- **Ядро**: матчинг транзакций с контрагентами/контрактами ВЭД/инвойсами, курсы, партии ФИФО;
- **Слой 1С**: выгрузка проектов документов через HTTP-сервис, идемпотентность по хэшу;
- **Отчётность**: справки для банка/депозитария, журнал операций для ФНС, журнал неизменяемости (сырые ответы нод).

Принципы, которые **нельзя нарушать**: read-only (никаких приватных ключей и подписания транзакций), 1С — мастер-система учёта, неизменяемость первички, обновляемые шаблоны форм.

## 2. Зачем эта доработка (бизнес-контекст)

С 01.07.2027 учёт и хранение цифровой валюты в РФ переходит к цифровым депозитариям и лицензированным посредникам из реестра ЦБ. Юридически главным источником первички станет **выписка депозитария**; блокчейн-запись — доказательная база второго уровня. API депозитариев ещё не существует (подзаконные акты не изданы, лицензии не выданы).

Цель доработки: подготовить архитектуру так, чтобы при появлении реальных API интеграция сводилась к написанию **тонкого адаптера за 2–4 недели**, а у действующих клиентов новый режим включался **настройкой, без повторного внедрения**.

## 3. Не-цели (жёсткая граница скоупа — не делать)

- ❌ Никакой интеграции с реальными внешними API депозитариев/обменников (их нет).
- ❌ Никаких потоков аутентификации/OAuth/ключей к внешним кастоди-системам.
- ❌ Не менять логику ФИФО, проводок и выгрузки в 1С: в режимах `off`/`shadow` источник истины для учёта — блокчейн, как сейчас.
- ❌ Не реализовывать режим `active` (custody-first учёт) дальше заглушки с дизайн-заметкой.
- ❌ Не строить отдельный UI-продукт: максимум — вкладка «Сверка» в существующей админ-панели.
- ❌ Не изобретать форматы «под конкретный депозитарий»: канонические модели — нейтральные.

Если в ходе работы кажется, что нужно выйти за эти границы, — остановиться и зафиксировать вопрос в `specs/questions.md`, не реализовывать.

## 4. Архитектура

### 4.1. Абстракция источников данных

Ввести общий интерфейс источников и две семьи:

```
DataSource (abstract)
├── ChainSource      — существующие ChainAdapter (TRON, Ethereum) — рефакторинг без изменения поведения
└── CustodySource    — новый: DepositoryAdapter (депозитарии, лицензированные обменники)
```

Требования к рефакторингу `ChainSource`: существующие контракты `ChainAdapter` не ломать; вся текущая функциональность проходит регрессионные тесты без изменений.

### 4.2. Канонические модели

**`LedgerEntry`** — нормализованная on-chain транзакция (существующая модель; при необходимости — переименовать/обернуть, сохранив совместимость).

**`CustodyStatement`** — выписка депозитария за период:
- `statement_id`, `source_id` (какой адаптер), `period_from`, `period_to`, `issued_at`, `raw_payload` (неизменяемо), `checksum`.

**`CustodyEntry`** — строка выписки:
- `entry_id`, `statement_id`, `occurred_at`, `asset` (тикер + справочник соответствий), `network` (nullable), `amount` (Decimal, знак = направление), `operation_type` (`deposit | withdrawal | trade | fee | transfer_internal | other`), `counterparty_ref` (nullable), `external_tx_hash` (nullable), `raw_line` (неизменяемо).

Все внешние данные храним в двух слоях: сырой payload как получен (журнал неизменяемости, как для нод) + нормализованная модель.

### 4.3. Интерфейс `DepositoryAdapter`

```
interface DepositoryAdapter:
    meta() -> AdapterMeta            # id, версия, человекочитаемое имя
    capabilities() -> Capabilities   # has_tx_hash, has_counterparty, has_network,
                                     # entry_granularity: per_tx | aggregated | mixed
    fetch_statements(period) -> list[CustodyStatement]
    fetch_entries(statement_id) -> list[CustodyEntry]
    health() -> HealthStatus
```

- Регистрация через тот же plugin-registry механизм, что и `ChainAdapter`.
- Интерфейс версионируется (`adapter_api_version`), чтобы будущие реальные адаптеры объявляли совместимость.
- `capabilities()` — ключевой элемент: движок сверки обязан работать при ЛЮБОЙ комбинации (в т.ч. когда выписка не содержит tx-хэшей и агрегирует операции за день).

### 4.4. `MockDepositoryAdapter`

1. Читает фикстуры из CSV и JSON (оба формата; схемы задокументировать в `docs/custody-fixtures.md`).
2. **Генератор фикстур** — CLI-команда: берёт реальные проиндексированные chain-данные за период и производит из них «выписку депозитария» с конфигурируемыми искажениями:
   - `--drop N` — потерять N записей (недостача в выписке);
   - `--extra N` — добавить N записей, которых нет в цепочке;
   - `--amount-noise` — исказить суммы (например, комиссия удержана внутри суммы);
   - `--date-shift` — сдвиг дат, в т.ч. через границу периода;
   - `--aggregate day|counterparty` — агрегированные строки (одна строка = несколько tx);
   - `--strip hashes|counterparty|network` — эмуляция бедной выписки (проверка capabilities).
3. Мок должен уметь эмулировать задержку и ошибки (`health()` degraded) — для тестов устойчивости.

### 4.5. Движок сверки (Reconciliation Engine)

Вход: множество `LedgerEntry` (final) и множество `CustodyEntry` за период. Выход: результат сверки.

**Каскад матчинга (по убыванию приоритета):**
1. по `external_tx_hash` (если capability есть) — точное соответствие;
2. по кортежу `(asset, amount ± tolerance, occurred_at ± date_window, direction)`;
3. агрегатный матчинг: одна `CustodyEntry` ↔ N `LedgerEntry` (и наоборот), если суммы сходятся в пределах tolerance и entries попадают в окно (для `entry_granularity = aggregated`);
4. всё остальное — в очередь ручного разбора (переиспользовать существующий механизм manual-queue из матчинга контрактов; оператор связывает вручную, связка запоминается).

**Статусы результата:** `matched | matched_aggregate | missing_in_custody | missing_on_chain | amount_mismatch | date_mismatch | duplicate_suspect | manual`.

**Конфигурация** (per-client, в настройках): `tolerance` (абсолютная и относительная), `date_window`, приоритет правил, автоматическое принятие агрегатов (on/off).

**Свойства:** детерминированность (одинаковый вход → одинаковый результат), идемпотентность повторного запуска, полный аудит-лог решений движка (какое правило сработало, почему).

### 4.6. Отчёт о расхождениях

- Печатная форма «Акт сверки: блокчейн ↔ депозитарий за период» — через существующий модуль обновляемых шаблонов: сводка (кол-во/суммы по статусам) + построчная детализация с хэшами и ссылками.
- Экспорт PDF и XLSX.
- В 1С в режиме `shadow` — только регистр сведений «Результаты сверки с депозитарием» (информационный), **никаких** бухгалтерских документов.

### 4.7. Режимы работы (та самая «галочка»)

Настройка `custody_mode`:

| Режим | Поведение |
|---|---|
| `off` (по умолчанию) | Текущее поведение продукта. Ничего из custody-слоя не активно. |
| `shadow` | Загрузка выписок (mock или будущий реальный адаптер), сверка, отчёты, вкладка «Сверка» в админке. Источник истины для учёта — блокчейн. Нулевое влияние на проводки. |
| `active` | ЗАГЛУШКА. При включении — явная ошибка «режим будет доступен после вступления требований в силу» + ссылка на дизайн-заметку. |

Для `active` написать **дизайн-заметку** `docs/adr/ADR-00X-custody-first.md`: как поменяются источник истины, генерация документов 1С, миграция клиента `shadow → active`, обратная совместимость. Только документ, без кода.

## 5. Данные и хранение

- Новые таблицы: `custody_statements`, `custody_entries`, `reconciliation_runs`, `reconciliation_results`, `custody_asset_mapping` (тикер выписки ↔ актив системы).
- Миграции — через существующий механизм миграций; откатываемые.
- Сырые payload'ы выписок — в журнал неизменяемости по той же схеме, что ответы нод.

## 6. Тестовые сценарии (обязательные, зафиксировать как автотесты)

1. Идеальное совпадение 1:1 по хэшам.
2. Недостача: запись есть в цепочке, нет в выписке → `missing_in_custody`.
3. Лишняя запись в выписке → `missing_on_chain`.
4. Расхождение суммы на величину комиссии → `amount_mismatch` при tolerance=0; `matched` при tolerance ≥ комиссии.
5. Сдвиг даты через границу отчётного периода → корректная работа `date_window`.
6. Агрегированная строка выписки = 5 chain-транзакций за день → `matched_aggregate`.
7. Частичное покрытие агрегата (4 из 5 tx) → расхождение с указанием дельты.
8. Дубликат строки в выписке → `duplicate_suspect`, не двойной матч.
9. Другой тикер того же актива (маппинг активов) → `matched` через `custody_asset_mapping`.
10. Реорг после выпуска выписки: chain-транзакция потеряла финальность → результат сверки помечается устаревшим, повторный запуск даёт консистентный итог.

Плюс: регрессионный прогон всего существующего функционала при `custody_mode = off` — поведение бит-в-бит прежнее.
