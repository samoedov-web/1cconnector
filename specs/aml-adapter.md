# ТЗ: AML-слой и поток ожидаемых платежей (по регламенту оплаты)

> Источник требований: `specs/payment-regulation.md` (шаги 2–5, сценарий 1).
> Работать по фазам из раздела 6 — по одной фазе за сессию, с тестами.
> Вопросы фиксировать в разделе 7, не додумывать.

## 1. Контекст

Регламент оплаты требует AML-проверку адреса получателя **до отправки
средств** (шаг 3) и статусную машину ожидаемого платежа: инвойс →
проверка → разрешение казначею → отправка → привязка транзакции.
Сегодня коннектор работает пост-фактум (транзакция → матчинг); адрес
нерезидента из инвойса уже попадает в справочник до платежа (реализовано),
но проверки и разрешительного потока нет.

Принципы продукта сохраняются: коннектор **read-only** — отправляет
казначей из внешнего кошелька; коннектор выдаёт/блокирует разрешение
и фиксирует доказательную базу.

## 2. Не-цели (жёсткая граница)

- ❌ Не подписывать и не отправлять транзакции, не хранить ключи.
- ❌ Не блокировать техническими средствами внешний кошелёк — «блокировка»
  = отсутствие разрешения в интерфейсе и алерт при нарушении порядка.
- ❌ Не зашивать конкретного провайдера: Crystal — первый адаптер,
  интерфейс нейтральный (Chainalysis/TRM/Шард — теми же адаптерами).
- ❌ Не изобретать скоринг: risk_score и категории — как отдаёт провайдер;
  пороги — конфигурация.

## 3. Архитектура

### 3.1. AmlAdapter (семейство aml в реестре источников)

```
interface AmlAdapter(DataSource):
    meta() / health()                      # как у других семейств
    screen_address(network, address) -> AmlResult
AmlResult: risk_score (0–100), categories (sanctions|darknet|mixer|...),
           provider_ref, raw (журнал неизменяемости), screened_at
```

Реализации: `CrystalAdapter` (API-ключ в конфигурации клиента),
`MockAmlAdapter` (фикстуры: адрес → скор; для тестов и демо).

### 3.2. ExpectedPayment (шаг 2 регламента)

Создаётся автоматически из инвойса с crypto_address (синхронизация 1С).
Поля: invoice_id, contract (УНК, КВВО), amount/currency, expected_asset,
to_address, network, tolerance, status, aml_result_id.

Статусы: `pending_aml → aml_approved | aml_review | aml_rejected →
sent → matched` (+ `expired` по сроку). Пороги по умолчанию из
регламента: 0–30 approved, 31–70 review, 71–100 rejected —
конфигурируемо.

### 3.3. Разрешительный поток

- `aml_review` → задача комплаенс-офицеру (новая роль RBAC `compliance`);
  решение с комментарием — в аудит-лог.
- `aml_approved` → экран казначея (роль `treasurer`): список «одобрено
  к отправке» (инвойс, сумма, адрес, срок действия одобрения).
- Индексер связывает исходящую транзакцию с ExpectedPayment
  (to_address + сумма ± tolerance) → `sent` → обычный конвейер → `matched`.
- Исходящая транзакция БЕЗ approved-ожидания → алерт «отправка вне
  регламента» + пометка в карточке.
- Ре-скрининг справочника адресов по расписанию; смена скора → алерт.

### 3.4. Интеграция с существующим

- Результат AML — в payload документа 1С (комментарий, шаг 9), в
  уведомление ФНС (блок AML, шаг 11), в акт по платежу.
- Сырые ответы провайдера — журнал неизменяемости (та же схема).
- Лицензирование: AML-функции доступны с пакета «Бизнес» (уточнить).

## 4. Данные

`aml_results` (неизменяемая первичка: raw + checksum), `expected_payments`,
`aml_address_status` (последний скор адреса, для ре-скрининга).

## 5. Definition of Done

- [ ] AmlAdapter + реестр (семейство aml) + Crystal + мок с фикстурами.
- [ ] ExpectedPayment: автосоздание из инвойса, статусная машина, сроки.
- [ ] Пороговая конфигурация, решение комплаенса, экран казначея.
- [ ] Связывание исходящей транзакции, алерт «вне регламента».
- [ ] Ре-скрининг по расписанию.
- [ ] AML-результат в документе 1С, уведомлении ФНС, акте по платежу.
- [ ] Аудит-цепочка шага 13 регламента: invoice → address → score →
      status → tx_hash → document → notification.
- [ ] Роли compliance/treasurer в RBAC и панели.

## 6. Фазировка

| Фаза | Содержимое |
|---|---|
| 1 | AmlAdapter + реестр + мок + модель aml_results (журнал неизменяемости) |
| 2 | ExpectedPayment: модель, автосоздание из инвойсов, статусная машина, скрининг при создании |
| 3 | Роли compliance/treasurer, экраны (очередь review, «одобрено к отправке»), решения в аудит |
| 4 | Связывание исходящих, алерт «вне регламента», ре-скрининг по расписанию |
| 5 | Прокидка AML в документ 1С / уведомление ФНС / акт; CrystalAdapter по их API-доке |

## 7. Вопросы (не додумывать)

- Срок действия одобрения AML до отправки (регламент не задаёт; предложение: 72 ч, потом повторный скрининг)?
- Скрининг входящих (пост-фактум) — в этой же спеке фазой 6 или отдельно? Регламент покрывает только исходящие.
- Пакет лицензии, с которого доступен AML-слой?
- Crystal: тариф/ключ — заводит клиент или вендор?
